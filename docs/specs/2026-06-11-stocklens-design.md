# StockLens — дизайн системы

- **Дата:** 2026-06-11
- **Статус:** на ревью
- **Курс:** Python & Data Science, семестровый проект «DataPulse»
- **Команда:** 2 человека (объём рассчитан с множителем), целевая оценка «5» + бонусы

---

## 1. Цели и контекст

StockLens — персональный аналитический веб-сервис по российскому фондовому рынку.
Ежедневный сбор котировок Мосбиржи и финансовых новостей → детерминированная аналитика
и ML-прогнозы → веб-дашборд + Telegram-алерты.

Назначение двойное:

1. **Семестровый проект** по единой архитектуре курса (ingestor → PostgreSQL → ML →
   FastAPI → Streamlit → Docker Compose) на уровень «5» + бонусные баллы
   (временные ряды, NLP, Telegram-бот, деплой на VPS).
2. **Реальный инструмент** для владельца, начинающего инвестировать: мониторинг рынка
   и портфеля, риск-аналитика, дайджесты новостей, обучение на бэктестах до вложения
   реальных денег.

Принцип честности ML: основную ценность дают **детерминированные** функции
(портфельная аналитика, дивидендный календарь, дайджесты — они не могут «ошибаться»),
а ML-прогнозы занимают методологически честное место (волатильность — единственное,
что в финансах устойчиво прогнозируется).

**Стандарт качества.** Критерии курса — нижняя граница, не цель. Целевой стандарт —
production-grade система: эталонная слоистая архитектура, код enterprise-уровня
(SOLID, Clean Architecture, строгая типизация, TDD для бизнес-логики), осознанные
архитектурные решения с зафиксированными обоснованиями. Слово «учебный» не является
оправданием для упрощений, ломающих архитектуру.

## 2. Не-цели

Явно **не делаем** — и это осознанные решения, а не упущения:

- **Точечный прогноз цены/доходности.** На дневном горизонте не отличим от random walk
  (слабая форма эффективности рынка). В EDA-ноутбуке демонстрируем это сравнением
  с naive baseline — как аргумент защиты, почему задача выбрана иначе.
- **Торговые сигналы / автоторговля.** Инструмент аналитический, не брокерский.
- **Мультипользовательность и авторизация в приложении.** Один пользователь (владелец);
  доступ к публичному инстансу ограничивается на уровне reverse proxy (Dokploy).
- **Внутридневные данные.** Только дневные свечи: для целей проекта и пользователя
  intraday не нужен, а анонимный доступ MOEX отдаёт его с задержкой 15 минут.
- **yfinance / зарубежные рынки.** Yahoo Finance заблокирован в РФ и нестабилен для
  cron-сбора — вычеркнут по результатам исследования источников.

## 3. Источники данных (проверены 2026-06-11)

| # | Источник | Что берём | Доступ | Документация |
|---|----------|-----------|--------|--------------|
| 1 | **MOEX ISS API** | Дневные свечи (~45 тикеров IMOEX), дивиденды, сплиты, значения индекса IMOEX | Без ключа и регистрации, JSON, история с 2013 г., пагинация 500 строк | [moex.com/a2193](https://www.moex.com/a2193), [iss.moex.com/iss/reference](https://iss.moex.com/iss/reference/) |

## 4. Архитектура

Микросервисы в Docker Compose, 7 контейнеров:

```
                    ┌────────────┐
   MOEX ISS ──────► │  ingestor  │       ┌─────────┐
   RSS (3 фида) ──► │ APScheduler├──────►│PostgreSQL│◄──────────┐
   ЦБ РФ ─────────► │  backfill  │       └────┬────┘            │
                    └────────────┘            │                 │
                                              ▼                 │
   ml/training (офлайн) ──► MLflow ──────► ┌─────┐   ┌──────────┴─┐
        │  эксперименты,    реестр         │ api │◄──│ dashboard  │
        └─ артефакты joblib ─────────────► │FastAPI   │ Streamlit │
                                           └──▲──┘   └────────────┘
                                              │       ┌─────┐
                                   Redis ◄────┴───────│ bot │ aiogram
                                  (кэш)               └─────┘
```

| Сервис | Ответственность | Технологии |
|--------|-----------------|------------|
| `db` | Хранилище | postgres:16-alpine, volume |
| `redis` | Кэш тяжёлых API-ответов | redis:7-alpine |
| `ingestor` | Сбор по расписанию + backfill при старте | APScheduler, requests, SQLAlchemy |
| `api` | REST: данные, прогнозы, портфель; инференс моделей | FastAPI, Pydantic, uvicorn |
| `dashboard` | UI, 6 страниц; ходит **только в API**, не в БД | Streamlit, Plotly |
| `bot` | Дайджесты и алерты; потребитель API | aiogram |
| `mlflow` | Трекинг экспериментов и реестр моделей | mlflow server |

Архитектурные инварианты:

- **Один write-путь в БД** — только `ingestor` (и Alembic-миграции). API читает;
  исключение — таблицы портфеля и подписок бота, которыми владеет API.
- **Dashboard и bot не знают про БД** — только HTTP к API. Это даёт чистые границы
  и независимое тестирование.
- **Общий код** (SQLAlchemy-модели, Pydantic-настройки, доменные enum'ы) — пакет
  `packages/stocklens-core`, устанавливается в образы ingestor и api как path-зависимость.
  Один источник истины для схемы данных.
- Часовой пояс: в БД — UTC (`timestamptz`); торговые даты — `date` по календарю биржи;
  отображение — Europe/Moscow.

## 6. Модель данных

| Таблица | Ключевые поля | Примечания |
|---------|---------------|------------|

| `dividends` | `security_id`, `ex_date`, `value`, `currency` | для календаря отсечек и коррекции гэпов в волатильности |

| `news_sentiment` | `article_id`, `label`, `score`, `model_version` | label: `StrEnum` positive/neutral/negative |
| `news_tickers` | `article_id`, `security_id` | связь новость↔бумага по словарю aliases |
| `portfolio_positions` | `security_id`, `quantity`, `avg_price`, `opened_at` | один пользователь |
| `predictions` | `security_id`, `predicted_for`, `horizon_days`, `kind`, `value`, `model_version`, `created_at` | kind: `StrEnum` volatility/trend; хранение прогнозов для страницы «прогноз vs факт» |
| `collector_runs` | `source`, `started_at`, `finished_at`, `status`, `records_added`, `error_message` | status: `StrEnum` success/partial/failed; основа страницы мониторинга |

Все статусы и типы — через `StrEnum` (хардкод строк в логике запрещён).

## 7. Ingestor

Расписание (APScheduler, cron-триггеры, таймзона Europe/Moscow):

| Задача | Когда | Логика |
|--------|-------|--------|
| Свечи + индекс | ежедневно 23:55 МСК | за сегодня по всем активным тикерам; upsert |
| Дивиденды, сплиты | ежедневно 08:00 | полный снапшот, upsert |
| Курсы ЦБ | ежедневно 13:00 | курс на завтра публикуется ~12:00 |
| RSS-новости | каждые 30 минут | парсинг фидов, дедуп по url, матчинг тикеров, скоринг sentiment |

Свойства:

- **Backfill при старте:** для каждого тикера смотрим последнюю дату свечи и догружаем
  пропуск из истории MOEX (история в API есть — пропущенные дни котировок
  восстановимы всегда). Новости восстановлению не подлежат — поэтому прод-инстанс
  на VPS запускается как можно раньше.
- **Идемпотентность:** все записи — upsert по натуральному ключу; повторный запуск
  безопасен.
- **Журналирование:** каждый запуск пишет строку в `collector_runs`; ошибка одного
  источника не валит остальные (partial-статус).
- Sentiment-скоринг новостей выполняется в ingestor сразу при сборе (модель локальная,
  лёгкая) — API отдаёт уже готовые оценки.

## 8. ML-пайплайн

### 8.1. Прогноз волатильности — основная задача

- **Таргет:** реализованная волатильность следующих 5 торговых дней
  (std лог-доходностей; альтернативная оценка по OHLC — Parkinson — в EDA).
- **Модели:** GARCH(1,1) (пакет `arch`) и HAR-RV (линейная регрессия на RV за 1/5/22 дня).
- **Baseline:** «волатильность завтра = волатильность вчера» (random walk RV).
- **Метрики:** QLIKE (основная для волатильности), RMSE.
- **Подготовка данных:** сессии выходного дня исключаются (`is_weekend_session`),
  дивидендные гэпы корректируются по таблице `dividends`, разрыв торгов 2022 г.
  обрабатывается явно (обучение на пост-2022 как основной вариант, сравнение — в EDA).

### 8.2. Sentiment новостей — NLP-бонус

- **Модель:** предобученная русскоязычная модель на базе rubert-tiny2
  (кандидат — `cointegrated/rubert-tiny-sentiment-balanced`; финальный выбор —
  при реализации, проверив актуальность на Hugging Face). CPU-инференс, ~120 МБ.
- **Baseline:** словарный метод (тональный словарь).
- **Оценка:** F1 на собственной размеченной выборке из ~200 заголовков
  (ручная разметка — честная валидация вместо слепого доверия предобученной модели).
- **Агрегация:** средний тон по тикеру за день → фича для тренда + триггер алертов.

### 8.3. Классификация тренда — вспомогательная

- **Таргет:** направление за следующие 5 торговых дней (вверх/вниз).
- **Модель:** CatBoost; **объяснимость:** SHAP в дашборде.
- **Фичи:** лаги доходностей, RSI, MACD, z-score объёма, реализованная волатильность,
  агрегаты sentiment.
- **Baseline:** «всегда вверх» (~50%). Ожидание — 52–55% accuracy; результат честно
  позиционируется как вероятностная оценка, не торговый сигнал.

### 8.4. Портфельная оптимизация — детерминированная аналитика

Марковиц (efficient frontier) поверх исторических доходностей; сравнение
с равными весами и IMOEX по Sharpe и максимальной просадке. Не ML — но ключевая
страница пользы и демо.

### 8.5. Методология

- **Валидация только walk-forward / `TimeSeriesSplit`.** Случайный K-fold запрещён —
  главный источник утечек в студенческих финансовых проектах. Скейлеры и фичи
  фитятся только на train-окне.
- **MLflow:** каждый запуск обучения логирует параметры, метрики, артефакт;
  лучшая модель регистрируется в реестре; API загружает модель по имени и версии,
  версия отображается в UI и пишется в `predictions`.
- **Переобучение:** еженедельный ручной запуск скриптов `ml/training` (автоматизация
  переобучения — вне объёма семестра, в README помечается как направление развития).

## 9. API-сервис (FastAPI) — эталонная реализация

API проектируется как образцовый FastAPI-сервис, а не «ручки поверх ORM».

### 9.1. Слоистая архитектура

```
routers/      → HTTP-слой: маршруты, статус-коды, response_model. Без бизнес-логики.
services/     → бизнес-логика: портфельная математика, оркестрация прогнозов,
                правила алертов. Не знает про HTTP.
repositories/ → доступ к данным: запросы SQLAlchemy, кэш Redis. Не знает про бизнес-правила.
schemas/      → Pydantic v2 DTO (вход/выход), строго отделены от ORM-моделей.
core/         → конфигурация (pydantic-settings), DI-провайдеры, исключения, логирование.
ml/           → загрузка моделей из MLflow, инференс-адаптеры.
```

Зависимости направлены строго вниз (router → service → repository); инверсия —
через `Depends` и протоколы (`typing.Protocol`) для repository-интерфейсов, что
позволяет подменять слой данных в unit-тестах без поднятия БД.

### 9.2. Async-стек

- Полностью асинхронный путь запроса: `asyncpg` + SQLAlchemy 2.0 `AsyncSession`,
  `redis.asyncio`. Никаких блокирующих вызовов в обработчиках; CPU-bound инференс —
  через `run_in_threadpool`.
- ORM-модели в `stocklens-core` engine-агностичны: API использует async-движок,
  ingestor — синхронный (осознанно: батчевый сбор не выигрывает от async,
  а простота коллекторов важнее).

### 9.3. Контракты

- Версионирование с первого дня: все маршруты под `/api/v1`.
- Pydantic v2-схемы на вход и выход, `response_model` на каждом маршруте;
  обогащённая OpenAPI-документация (описания, примеры, теги по доменам).
- Пагинация, сортировка и фильтры — единый переиспользуемый механизм
  (общие query-параметры через Depends), не копипаста по маршрутам.

### 9.4. Обработка ошибок

- Иерархия доменных исключений (`SecurityNotFoundError`, `InsufficientDataError`,
  `ModelNotLoadedError`…) → централизованные exception handlers → единый формат
  ответа об ошибке (RFC 9457 Problem Details: `type`, `title`, `detail`, `status`).
- Сообщения 4xx — по-русски и с контекстом: «Не удалось построить прогноз: по тикеру
  ABCD нет данных за выбранный период». Голые `raise Exception` и пустые `except`
  запрещены.

### 9.5. Наблюдаемость

- Структурные логи (structlog, JSON в проде, человекочитаемые в dev).
- Middleware: request-id (сквозной идентификатор в логах и заголовке ответа),
  тайминг запроса.
- `GET /api/v1/health/live` (процесс жив) и `GET /api/v1/health/ready`
  (БД + Redis + модели загружены) — раздельные liveness/readiness для healthcheck'ов
  Docker и Dokploy.

### 9.6. Жизненный цикл

- `lifespan`-контекст (не устаревшие `on_event`): прогрев — пул соединений БД,
  подключение Redis, загрузка ML-моделей из реестра; graceful shutdown — корректное
  закрытие пулов.
- Конфигурация — только через `pydantic-settings` из окружения; никаких чтений
  `os.environ` по коду.

### 9.7. Эндпоинты

| Метод и путь (под `/api/v1`) | Назначение |
|--------------|------------|
| `GET /health/live`, `GET /health/ready` | liveness / readiness |
| `GET /data/securities` | справочник бумаг |
| `GET /data/candles` | свечи: фильтры по тикеру/датам, пагинация, сортировка |
| `GET /data/news` | новости с sentiment: фильтры по тикеру/тональности/датам |
| `GET /data/dividends` | дивидендный календарь |
| `POST /predict/volatility` | прогноз волатильности по тикеру (+ метрики модели) |
| `POST /predict/trend` | вероятность роста + SHAP-вклады фич |
| `GET/POST/DELETE /portfolio/positions` | CRUD позиций портфеля |
| `GET /portfolio/summary` | P&L, сравнение с IMOEX, риск-метрики |
| `POST /portfolio/optimize` | efficient frontier, рекомендованные веса |
| `GET/POST/DELETE /bot/subscriptions` | подписки бота на алерты (бот не ходит в БД напрямую) |
| `GET /monitoring/runs` | журнал сборов для страницы мониторинга |

Redis-кэш тяжёлых ответов (свечи за длинные периоды, оптимизация портфеля) живёт
в repository-слое с TTL, согласованным с расписанием сбора.

| Страница | Содержимое |
|----------|-----------|
| 1. Обзор рынка | KPI-карточки (IMOEX, курсы, ставка ЦБ), топ роста/падения дня, время последнего обновления данных |

| 5. Портфель | позиции и P&L vs IMOEX, риск-метрики, efficient frontier, бэктест «купил поровну N месяцев назад» |
| 6. Мониторинг | статус источников (работает/сбоит), журнал `collector_runs`, последние ошибки |

Streamlit обращается только к API; на каждой странице обрабатываются три ветки
сетевого вызова: успех / ошибка сервера / сеть недоступна (пустых экранов без
объяснения нет).

## 11. Telegram-бот (aiogram)

- **Утренний дайджест** (08:30 МСК): IMOEX и портфель за вчера, дивидендные отсечки
  ближайшей недели, негативные новости по бумагам портфеля.
- **Алерты** (по подпискам в `bot_subscriptions`): всплеск негативного sentiment
  по бумаге портфеля; смена режима волатильности (прогноз выше порога);
  приближение дивидендной отсечки; цена пересекла заданный пользователем уровень.
- Команды: `/start`, `/digest` (по запросу), `/portfolio`, `/subscribe`, `/unsubscribe`.
- Бот — потребитель API; собственной бизнес-логики расчётов не содержит.

## 12. Качество

- **TDD** для всей бизнес-логики (Red → Green → Refactor): коллекторы (HTTP мокается
  через `respx`/`responses`), расчёт фич и волатильности, портфельная математика,
  сервисный слой API. Имена тестов — на английском, описывают сценарий
  (`predict_volatility_returns_404_for_unknown_ticker`).
- **Пирамида тестов:** unit (сервисы с подменёнными repository-протоколами, без БД) →
  интеграционные (repositories против реального PostgreSQL через testcontainers;
  API через `httpx.AsyncClient` + ASGI) → smoke compose-стека в CI.
- **Покрытие:** порог в CI — 50% (критерий курса как нижняя граница);
  целевой ориентир для сервисного и repository-слоя — ≥80%.
- **CI (GitHub Actions):** ruff check + ruff format --check → mypy → pytest с coverage →
  сборка всех Docker-образов. Прогон на PR и push в main.
- **pre-commit:** ruff, ruff-format, проверка секретов.
- **Типизация:** mypy strict для **всех** сервисов и `stocklens-core`; запрет `Any`
  и нетипизированных dict — Pydantic/TypedDict/Protocol на всех границах.
- **Линт-конфиг:** общий в корне (`pyproject.toml` верхнего уровня), ruff в строгом
  наборе правил (включая `B`, `UP`, `SIM`, `PL`).
- **Актуальность API библиотек:** перед реализацией каждого модуля — сверка
  с актуальной документацией (context7/официальные доки), а не training data:
  FastAPI, SQLAlchemy 2.0 async, aiogram, MLflow, arch.

## 13. Конфигурация

Все секреты и окружение — `.env` (в репозитории только `.env.example`):
`DB_USER`, `DB_PASSWORD`, `DATABASE_URL`, `REDIS_URL`, `TELEGRAM_BOT_TOKEN`,
`API_URL`, `MLFLOW_TRACKING_URI`, `TICKERS_UNIVERSE` (по умолчанию состав IMOEX).
Конфиги сервисов — `pydantic-settings`, никаких magic-значений в коде.

## 14. Деплой

- **Локально:** `docker compose up --build` поднимает всё; healthcheck у каждого
  сервиса; README с инструкцией от нуля.
- **Прод (бонус):** VPS владельца, Dokploy (compose-стек), домен; дашборд и API
  за reverse proxy Dokploy с basic auth (инструмент персональный). Прод-инстанс
  ingestor работает 24/7 — корпус новостей копится непрерывно.
- Последовательность: сначала разворачиваем на VPS «скелет» (db + ingestor) как можно
  раньше — чтобы новости начали копиться, пока остальное в разработке.

## 15. Риски и митигации

| Риск | Митигация |
|------|-----------|
| Сессии выходного дня MOEX искажают сезонность/волатильность | Флаг `is_weekend_session` с первого дня; модели обучаются на будних сессиях |
| Дивидендные гэпы выглядят как падение цены | Коррекция доходностей по `dividends` при расчёте фич |
| Структурный разрыв 2022 г. | Основное обучение на пост-2022; сравнение периодов — в EDA |
| RSS без архива — дыры в корпусе новостей | Ранний запуск ingestor на VPS; локальные пропуски некритичны |
| Неофициальные лимиты MOEX | ≤1 req/s, backoff, журналирование отказов в `collector_runs` |
| Утечки в time-series валидации | Только walk-forward; фит препроцессинга на train; код-ревью этого блока |
| Предобученная sentiment-модель плоха на финансовых заголовках | Ручная контрольная выборка ~200 заголовков; fallback — дообучение логрега на TF-IDF |
